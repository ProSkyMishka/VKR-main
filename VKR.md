Москва 2025Реферат
Данный отчет описывает разработку и исследование гибридного алгоритма конвертации декларативного UI‑кода SwiftUI в веб‑представление на базе React + TypeScript с применением больших языковых моделей. Предлагаемый подход предназначен для кроссплатформенного предпросмотра и тестирования SwiftUI‑интерфейсов вне экосистемы Apple и операционной системы macOS.
Отчет включает анализ предметной области и существующих подходов к автоматической трансляции кода и генерации UI, обоснование выбора гибридной стратегии, а также описание проектируемого конвейера конвертации. Алгоритм сочетает детерминированное сопоставление базовых SwiftUI‑конструкций (feature mapping), генерацию кода с помощью LLM с использованием prompt/RAG и итеративную автоматическую валидацию результата. Валидация включает сборку и типовую проверку TypeScript, поведенческие тесты (обработка событий, изменение состояния, навигация), а также визуальную регрессию на основе сравнения скриншотов в браузере.
Результатом работы является архитектура и прототип конвертера SwiftUI→React/TypeScript, теоретико‑множественная формальная модель декларативного UI с доказательством свойств завершимости и сходимости алгоритма, а также экспериментальная валидация на стратифицированном датасете SwiftUI‑примеров, покрывающих layout‑контейнеры, базовые элементы, состояния и привязки, списки, навигацию и простые анимации. Полный метод достигает 100 % успешной сборки и 83,3 % прохождения поведенческих тестов. Разработанное решение может использоваться как основа для инструментов предпросмотра SwiftUI в браузере и для интеграции UI‑проверок в кроссплатформенные среды разработки и CI/CD.
Данная работа состоит из 3 глав, 4 рисунков, 6 таблиц. Использовано 12 источников.
Ключевые слова: большие языковые модели; SwiftUI; конвертация кода; гибридный алгоритм; React; TypeScript; генерация интерфейсов; RAG; формальная верификация; автоматическая валидацияAbstract
This report describes the development and evaluation of a hybrid algorithm for converting declarative SwiftUI UI code into a web representation based on React + TypeScript using large language models. The proposed approach targets cross-platform preview and testing of SwiftUI interfaces outside Apple’s ecosystem and macOS.
The report includes an overview of related work in automated code translation and UI generation, a rationale for choosing a hybrid strategy, and a detailed description of the proposed conversion pipeline. The algorithm combines deterministic feature mapping for core SwiftUI constructs, LLM-based code generation enhanced with prompt/RAG, and an iterative automated validation loop. Validation includes TypeScript compilation and type checking, behavioral tests (events, state updates, navigation), and browser-based visual regression via screenshot comparison.
The outcomes include the architecture and a prototype SwiftUI→React/TypeScript converter, a set-theoretic formal model of declarative UI with proofs of termination and convergence properties, and an experimental evaluation on a stratified dataset of SwiftUI examples covering layout containers, basic elements, state and bindings, lists, navigation, and simple animations. The full method achieves 100% build success and 83.3% behavioral test pass rate. The resulting solution can serve as a foundation for browser-based SwiftUI preview tools and for integrating UI checks into cross-platform development workflows and CI/CD pipelines.
The paper contains 3 chapters, 4 figures, 6 tables. 12 sources are used.

Используемые определения и термины
Анимация (Animation) — механизм визуального перехода между состояниями UI (например, изменение прозрачности/позиции/масштаба) при изменении состояния или структуры интерфейса.
AST (Abstract Syntax Tree, абстрактное синтаксическое дерево) — древовидное представление исходного кода, отражающее его синтаксическую структуру и используемое для анализа и трансформаций.
Baseline (бейзлайн) — простейший или стандартный вариант решения/конфигурации, с которым сравниваются улучшенные методы в эксперименте.
Binding (@Binding, привязка) — механизм SwiftUI для двунаправленной связи между состоянием (обычно родительским) и дочерним представлением; изменение значения в одном месте отражается в другом.
Build (сборка) — процесс компиляции и сборки проекта (в данной работе — React/TypeScript), используемый как автоматическая проверка корректности сгенерированного кода.
CI/CD — практики непрерывной интеграции и доставки, предполагающие автоматический запуск сборки, тестов и проверок при изменениях в коде.
CSS (Cascading Style Sheets) — язык описания стилей веб‑страниц, используемый для задания визуального оформления и layout.
DOM (Document Object Model) — объектная модель HTML‑документа в браузере; структура узлов, которую изменяют веб‑фреймворки при обновлении UI.
Feedback loop (контур обратной связи) — итеративная схема «генерация → проверка → исправление», где результаты проверок (ошибки компиляции, тестов, визуальные различия) используются для уточнения следующей генерации.
Feature mapping (сопоставление фич/конструкций) — набор детерминированных правил преобразования элементов SwiftUI (например, VStack, Text, `Button`) в эквивалентные веб‑конструкции (JSX/HTML/CSS).
HTML (HyperText Markup Language) — язык разметки веб‑страниц; в работе выступает базой для итогового отображения React‑компонентов в браузере.
IR (Intermediate Representation, промежуточное представление) — структурированное представление программы/интерфейса, применяемое как “буферный” формат для трансформаций и анализа.
UI‑IR (промежуточное представление UI) — IR, описывающее дерево компонентов интерфейса, модификаторы, состояние, события, навигацию и (в минимальном виде) анимации.
JSX — синтаксическое расширение JavaScript/TypeScript для описания дерева React‑элементов, используемое как основная форма представления UI в React.
Layout (раскладка) — правила вычисления размеров и позиционирования элементов интерфейса (в SwiftUI и в web/CSS отличаются и требуют сопоставления).
LLM (Large Language Model, большая языковая модель) — нейросетевая модель, обученная на больших массивах текста/кода и способная генерировать код по запросу и контексту.
Linting (линтинг) — статическая проверка кода на соответствие правилам стиля и потенциальные ошибки (например, ESLint для TypeScript).
Modifier (модификатор SwiftUI) — операция, применяемая к View для изменения его внешнего вида или поведения (например, .padding(), .background(), `.onTapGesture()`).
Navigation (навигация) — механизм переходов между экранами/состояниями приложения (в SwiftUI — NavigationStack/NavigationLink, в web обычно реализуется роутером).
Prompt (промпт) — входное текстовое задание для LLM, содержащее инструкцию, контекст, примеры и ограничения генерации.
RAG (Retrieval‑Augmented Generation) — подход, при котором перед генерацией LLM система извлекает релевантные примеры/правила из базы знаний и добавляет их в prompt для повышения качества и устойчивости результата.
Screenshot regression (визуальная регрессия) — автоматическая проверка UI, основанная на сравнении скриншотов текущего результата с эталонными изображениями.
State (@State) — локальное состояние SwiftUI‑компонента; изменение @State инициирует пересчёт body и обновление UI.
TypeScript — типизированный надмножество JavaScript, используемое в работе как целевой язык для генерации веб‑кода и последующей типовой валидации.
Unit test (модульный тест) — тест, проверяющий корректность отдельных функций/компонентов (например, корректность обновления состояния при клике).
Smoke test (smoke‑тест) — быстрый тест “на работоспособность” (например, приложение собирается и рендерит основной экран, базовые действия не падают).
View (SwiftUI View) — базовая единица композиции SwiftUI‑интерфейса; описывает отображение как функцию от состояния.
Diffing (диффинг) — вычисление различий между двумя версиями дерева UI/DOM для выполнения минимального обновления интерфейса.
Reconciliation (реконсиляция) — процесс приведения фактического UI (DOM/дерева компонентов) к целевому состоянию после изменения данных; в React и SwiftUI реализуется по-разному.
Введение
В последние годы наблюдается стремительное развитие инструментов декларативного программирования пользовательских интерфейсов, среди которых ключевую роль занимает фреймворк SwiftUI, предназначенный для платформ Apple. SwiftUI основан на декларативной парадигме и тесно интегрирован в экосистему Xcode и macOS. Однако, в отличие от веб-фреймворков вроде React или Vue, разработка и визуализация SwiftUI-кода возможны исключительно в операционной системе macOS, что существенно ограничивает его потенциал.
В условиях распространения моделей искусственного интеллекта, способных к семантическому анализу и генерации программного кода, возникает возможность создания инструментов, обеспечивающих автоматическую конвертацию SwiftUI-интерфейсов в веб-представление. Такая конвертация позволяет воспроизводить и тестировать SwiftUI-приложения вне среды Apple, включая Windows, Linux и браузерные платформы.
Предлагаемая работа направлена на разработку гибридного алгоритма конвертации SwiftUI-кода в веб-представление с применением больших языковых моделей (LLM), объединяющего формальные методы синтаксического сопоставления и генерацию кода на основе больших языковых моделей.Глава 1. Анализ предметной области и обоснование разработки
Введение в предметную область: декларативные интерфейсы и задача кроссплатформенной визуализации
Пользовательский интерфейс (UI) является ключевым компонентом современных программных систем. Качество UI влияет на удобство, доступность и эффективность использования продукта, а также на стоимость сопровождения и развития. Исторически интерфейсы в большинстве платформ создавались в императивной парадигме (например, UIKit на iOS, Android Views, классический DOM‑подход), где разработчик явно создаёт элементы, управляет их состоянием и вручную обновляет отображение.
В последние годы широкое распространение получили декларативные UI‑фреймворки, где интерфейс описывается как функция состояния приложения: изменение состояния приводит к автоматическому обновлению UI. Наиболее известные представители:

- SwiftUI (Apple) — интерфейсы для iOS/macOS/watchOS/tvOS;
- React (web) — интерфейсы в браузере;
- Jetpack Compose (Android) — декларативный UI на Kotlin;
- Flutter — декларативный UI (Dart) с собственным движком рендеринга.
Общая идея декларативного UI: разработчик задаёт что должно отображаться при данном состоянии, а фреймворк определяет, как минимально обновить отображение (через реконсиляцию/диффинг, внутренние стратегии layout и т.п.). Декларативный подход упрощает композицию компонентов, повторное использование кода и снижение количества “ручных” ошибок, связанных с неконсистентным состоянием UI.
Одновременно возникает практическая проблема: UI‑код становится тесно связанным с инструментальной цепочкой платформы. Для SwiftUI это выражено особенно сильно: разработка и предпросмотр UI традиционно строятся вокруг Xcode и macOS.
SwiftUI как технология: модель построения UI, особенности и ограничения
Основные сущности SwiftUI
SwiftUI — декларативный фреймворк, где интерфейс задаётся композицией сущностей, реализующих протокол View. Основные элементы:
Views — компоненты интерфейса, определяемые через var body: some View.
Композиция — вложенность элементов: контейнеры (VStack, HStack, ZStack), списки (List, ForEach), навигация (NavigationStack, NavigationLink) и т.д.
Модификаторы (modifiers) — функциональные преобразования view: .padding(), .frame(), .background(), .foregroundStyle(), .onTapGesture() и др. Модификаторы компонуются цепочкой и влияют на внешний вид или поведение.
Состояния и привязки — @State, @Binding, @ObservedObject, @EnvironmentObject: UI является функцией состояния; изменение состояния инициирует пересчёт body и обновление UI.
События — обработчики действий пользователя: Button, жесты, .onChange и т.д.
Анимации — withAnimation, .animation, .transition, а также анимируемые параметры в layout.
Почему SwiftUI сложно переносить в веб “как есть”
Несмотря на декларативность, SwiftUI опирается на собственную модель layout и поведение:
Layout‑семантика в SwiftUI отличается от CSS: приоритеты размеров, поведение Spacer, правила align/spacing, измерение размеров, порядок применения модификаторов.
Идентичность и реконсиляция (особенно в списках) влияют на обновления и анимации.
Навигация и жизненный цикл в SwiftUI не являются прямыми аналогами web‑роутинга.
Анимации в SwiftUI могут иметь семантику, не совпадающую с CSS animations.
Инструментарий (previews/инспекция/сборка) тесно интегрирован в экосистему Apple.
Практическое ограничение инструментов SwiftUI
Критичное ограничение для темы ВКР: полноценная визуализация SwiftUI‑кода требует macOS (Xcode, симуляторы, Preview). Это создаёт барьеры:
обучение SwiftUI для студентов/команд без macOS;
кроссплатформенный code review UI (например, в браузере);
запуск автоматизированных UI‑проверок (в т.ч. визуальных) в универсальных CI/CD;
быстрая демонстрация UI‑прототипов в веб‑среде.
Обоснование разработки: зачем нужен SwiftUI → Web (React + TypeScript)
Ценность веб‑представления SwiftUI
Возможность конвертировать SwiftUI в web‑представление даёт следующие преимущества:
Кроссплатформенный предпросмотр: открытие и проверка интерфейса в браузере на любой ОС.
Упрощение совместной разработки: часть команды может смотреть UI и комментировать изменения без macOS.
Интеграция в CI/CD: автоматическая сборка/тесты/визуальная регрессия UI на инфраструктуре, где macOS недоступна или дорога.
Образовательные сценарии: учебные платформы и задания, где студент пишет SwiftUI, а преподаватель/система проверяет результат в вебе.
Целевое представление
Выбор React+TS обоснован следующими факторами:
React близок к SwiftUI по декларативной модели UI: “UI как функция состояния”.
TypeScript даёт сильный слой типовой валидации, снижая риск некорректного кода.
React является одним из стандартов UI разработки в web, что упрощает внедрение результата.
Постановка проблемы
Проблема семантической эквивалентности
Конвертация UI — не просто “переписать код”, а обеспечить сохранение наблюдаемого поведения. Для интерфейсов корректность обычно включает три уровня:
Структурная корректность: Сохранение дерева UI: вложенность, порядок, наличие ключевых элементов.
Поведенческая корректность: Сохранение реакции на события и изменения состояния (например, клики меняют @State, UI обновляется ожидаемо).
Визуальная близость: Сходство итогового рендера (layout, отступы, порядок наложения) до заданного допуска.
Полная эквивалентность SwiftUI runtime и web runtime невозможна в общем случае, поэтому исследование строится на:
ограниченном подмножестве SwiftUI конструкций,
формализованных метриках (build/tests/visual),
явных допущениях.
Ограничиваемое подмножество SwiftUI (для исследуемости)
Для ВКР фиксируется подмножество:
layout: VStack, HStack, ZStack;
элементы: Text, Image, Button;
состояние/привязки: @State, @Binding;
списки: List, ForEach;
навигация: NavigationStack, NavigationLink (базовый сценарий);
анимации: простые типовые (без сложных кастомных случаев).
Исключаются:
UIViewRepresentable и UIKit‑мосты,
сложные анимационные сценарии,
платформенно‑специфические API без web‑аналогов.
Подходы к решению задачи: классы методов
В литературе и практике решения задачи “UI → другое представление” встречаются три базовых класса подходов.
Правило‑ориентированные конвертеры (feature mapping)
Задаются детерминированные правила сопоставления конструкций:
VStack → flex‑column контейнер,
Text → /,
Button →  и т.д.
Плюсы:
предсказуемость и воспроизводимость,
объяснимость,
проще покрывать базовые элементы.
Минусы:
сложность модификаторов (композиция правил),
различия layout‑семантики SwiftUI и CSS,
трудность масштабирования на большие подмножества SwiftUI.
Вывод: необходимо как минимум как “скелет”, но недостаточно для реального кода.
Генерация LLM “целиком” (LLM-only)
LLM получает SwiftUI код и генерирует React+TS код полностью.
Плюсы:
потенциально широкое покрытие конструкций,
способность учитывать контекст и “догадаться” о паттернах.
Минусы:
нестабильность результата,
риск галлюцинаций API,
отсутствие гарантий семантики,
трудно автоматизировать без строгих проверок.
Вывод: LLM-only непригоден как инженерное решение без валидации.
Гибридный подход: rules + LLM + validation loop (выбранный)
разделяется ответственность:
rules: строят структуру и покрывают простые отображения;
LLM: заполняет неоднозначные части, переводит сложные модификаторы/паттерны;
validation loop: компиляция/тесты/визуальная регрессия → контрпример → исправление.
Вывод: Этот класс методов хорошо переносится на UI, где есть и статические, и поведенческие, и визуальные критерии корректности.
Аналоги и близкие решения (сравнительный анализ)
Поскольку прямого промышленного конвертера “SwiftUI → React” практически нет, аналоги разумно рассматривать как соседние классы решений, частично закрывающие проблему.

Минусы:
не дают полноценного конвейера проверки качества,

Альтернативные реализации SwiftUI‑подобного рантайма
Существуют проекты[2], которые пытаются реализовать SwiftUI‑совместимый API на других платформах (например, через альтернативные рендереры). Это другой класс решения: не конвертация в React, а перенос runtime.

Минусы:

Code translation с LLM (общий перенос кода)
Работы[3][4][5] по переводу между языками (в том числе на реальных проектах) показывают:
LLM могут переводить код, но падают на “настоящих” проектах без контекста,
гибридные методы и проверка компиляцией/типами повышают качество,
контекст репозитория и retrieval‑подходы улучшают результат.
Плюсы:
дают научную основу для гибридной стратегии и validation loop.
Минусы:
UI‑код требует дополнительной оценки через визуальные метрики и события.

Назначение и границы решения
Назначение
Разрабатываемое решение представляет собой инструмент (алгоритм + прототип) для конвертации SwiftUI‑кода в веб‑представление на базе React + TypeScript, предназначенное для:
кроссплатформенного предпросмотра SwiftUI‑интерфейсов в браузере;
автоматизированной проверки корректности конвертации (типизация, тесты, визуальная регрессия);
использования в учебных и инженерных сценариях, где часть пользователей не имеет доступа к macOS/Xcode.
Поддерживаемое подмножество SwiftUI 
Поддерживаются:
layout: VStack, HStack, ZStack;
элементы: Text, Image, Button;
состояние/привязки: @State, @Binding;
списки: List, ForEach;
навигация: NavigationStack, NavigationLink (базовый сценарий);
анимации: простые типовые (без сложных кастомных случаев).

- UIViewRepresentable и UIKit‑мосты,
сложные анимационные сценарии,
платформенно‑специфические API без web‑аналогов.

Генерировать структуру проекта (или компонент) в предсказуемом формате.
Выполнять автоматические проверки.

Нефункциональные требования
Воспроизводимость: при фиксированной конфигурации конвертация должна быть стабильной (структура файлов, стиль, выбранные паттерны).
Расширяемость: добавление новых правил маппинга и новых SwiftUI‑конструкций не должно требовать переписывания всего пайплайна.  
Отладочность: сохранять UI‑IR, промпты, результаты валидации и диффы как артефакты.
 Ограничение стоимости: лимитировать число LLM‑вызовов и объём контекста (особенно в repair loop).
Методологическая основа
Решение опирается на общую семантическую идею декларативного UI: интерфейс есть функция состояния, а пользовательские события индуцируют переходы состояния.
Практически это выражается в том, что конвертация должна сохранять:
структуру UI‑дерева,
точки чтения/изменения состояния (`@State`, `@Binding`),
обработчики событий,
(частично) анимации как реакцию на изменения state/структуры.
Для снижения неоднозначности и обеспечения воспроизводимости вводится UI‑IR — промежуточное представление интерфейса, независимое от SwiftUI и React.

Промежуточное представление UI (UI‑IR)

Рис. 3. Диаграмма UI-IR модели данных.
Назначение UI‑IR
Для обеспечения воспроизводимости и проверяемости конвертации вводится промежуточное представление пользовательского интерфейса (UI‑IR - User Interface Intermediate Representation). UI‑IR предназначено для отделения:
анализа исходного SwiftUI‑кода (синтаксических особенностей Swift);
от процедур генерации целевого веб‑кода (React/TypeScript).
Тем самым UI‑IR выступает в роли “семантического контракта” между этапами: парсером SwiftUI, rule‑mapping, retrieval‑модулем (RAG), генерацией LLM и валидаторами.
UI‑IR в рамках прототипа не претендует на полноту всего SwiftUI. Если парсер обнаруживает конструкцию вне поддерживаемого подмножества, она:
маркируется как Custom или добавляется в список “неразрешённых” фрагментов;
далее обрабатывается LLM (с RAG‑контекстом и валидацией), либо фиксируется как ограничение.
Состав UI‑IR (общая структура)
UI‑IR описывает интерфейс как набор взаимосвязанных моделей:
Модель дерева компонентов — фиксирует структуру UI (иерархию контейнеров и элементов).
Модель состояния и действий — фиксирует переменные состояния и абстрактные действия, изменяющие состояние.
Модель навигации — фиксирует набор экранов/маршрутов и переходов между ними.
Модель анимаций— фиксирует места, где требуется анимация или переходы (transition) при изменении состояния или структуры.
Модель дерева компонентов
Пусть  — конечное упорядоченное дерево, узлы которого соответствуют элементам интерфейса. Каждый узел () имеет:
тип компонента;
параметры (свойства);
список модификаторов;
список дочерних узлов;
(опционально) связи с состоянием и обработчиками событий;
(опционально) идентичность (ключ) для корректной реконсиляции списков.
Узел компонента () представляется структурой ComponentNode:
Тип компонента (type): Тип задаёт класс UI‑элемента
Параметры компонента (props): значения, необходимые для построения компонента (например, текст, имя изображения и т.п.).
Модификаторы (modifiers): операции, применяемые к компоненту, которые изменяют его внешний вид или поведение. Модификаторы хранятся как упорядоченный список, поскольку порядок их применения в SwiftUI может влиять на результат.
Дочерние элементы (children): упорядоченный список дочерних узлов, формирующий вложенность UI.
События (`events`): связывают компонент с реакцией на действие пользователя.
Идентичность (identity): ключ, обеспечивающий устойчивое соответствие элементов в коллекциях (аналог id в SwiftUI и key в React).
Модель состояния и действий
SwiftUI и React опираются на реактивную модель: изменение состояния приводит к обновлению UI. Поэтому при конвертации требуется не только перенести структуру, но и корректно сопоставить:
переменные состояния (`@State`) → useState;
привязки (`@Binding`) → props + callback/сеттор;
обработчики событий → функции, изменяющие состояние.
Структура StateModel содержит:
Переменные состояния (stateVars): Список объявлений состояния (name — имя переменной; type — тип; initial — начальное значение).
Привязки (bindings): Список привязок (name; type; source — источник привязки, то есть “чьё состояние проксируется”).
Действия (`actions`): абстрактная операция, инициируемая событием UI и приводящая к изменению состояния. 
Модель навигации
Навигация SwiftUI не является прямым аналогом веб‑роутинга, но её можно представить как ориентированный граф переходов между “экранами” (views).
NavigationModel включает:
Набор экранов/маршрутов (routes): Каждый маршрут описывается (name — логическое имя экрана; path — URL‑путь (для web); componentRef — ссылка на компонент, который отображается на этом маршруте).
Переходы (links): фиксируется как связь (fromRef — откуда осуществляется переход; toRoute — куда осуществляется переход; trigger — каким UI‑элементом инициируется переход).
Модель анимаций
Полная семантика анимаций SwiftUI сложна и зависит от runtime. В рамках ВКР поддерживаются простые случаи, поэтому в UI‑IR анимации фиксируются в виде “подсказок” (hints), которые:
указывают, что при изменении определённого состояния нужно применить анимацию;
задают типовую форму эффекта (например, opacity/scale/slide).
Список записей AnimationEntry, где каждая запись содержит:
trigger — какое изменение состояния или структуры запускает анимацию;
targetRef — к какому узлу/компоненту применить эффект;
kind — тип эффекта (например, opacity, scale, transition);
params — параметры (длительность, easing) в допустимом упрощённом виде.
Rule-based слой (feature mapping)
Роль правил
Правила выполняют “детерминированное ядро”, уменьшая свободу LLM и повышая воспроизводимость:
задают структуру JSX для базовых компонентов;
определяют базовую трансляцию layout;
формируют нормализованные style‑tokens из типовых модификаторов.
Границы правил
Правила покрывают только “надёжно отображаемое”. Всё, где:
требуется контекстный выбор (например, стилизация, сложные композиции модификаторов),
 нужно аккуратно перенести state/props в архитектуру React, — передаётся LLM, но в рамках строгого контракта и с валидацией.
RAG (Retrieval‑Augmented Generation)
Назначение
RAG используется для повышения качества и консистентности генерации:
дает LLM похожие “паттерны” перевода;
снижает вероятность неидиоматичных решений;
помогает с edge‑cases (List/ForEach key, navigation, частые модификаторы).
Корпус примеров
Корпус хранит микро‑примеры:
swiftui_snippet
ir_signature (типы узлов + теги: `layout/state/list/nav/anim/modifiers`)
react_snippet
notes (пояснение, почему так)
tags
Для прототипа достаточно 50–150 примеров, собранных вручную и расширяемых по мере экспериментов.
Retrieval‑стратегия 
извлекать примеры по совпадению тегов/структуры UI‑IR,
выбирать top‑k (например, k=3),
добавлять в prompt как “reference translations”.

LLM должна:

Генерация делится на 2-4 шага:
структура компонентов и state/props,

Глава 3. Формальные основания алгоритма и экспериментальная валидация
В данной главе формализуется предложенный гибридный алгоритм конвертации с использованием аппарата дискретной математики. Вводится теоретико‑множественная модель конвейера, определяются метрики качества и доказываются свойства завершимости и сходимости алгоритма. Далее описывается методика экспериментальной валидации, представляются и анализируются результаты эксперимента на датасете из 108 SwiftUI‑примеров.
3.1. Формальная модель декларативного UI
Предлагаемый алгоритм конвертации опирается на теоретико‑множественную модель декларативного пользовательского интерфейса, разработанную автором в рамках подготовки публикации «A Verified Core Model for Reactive User Interfaces: From SwiftUI to Cross‑Framework Semantics» [12]. Ниже приводятся ключевые определения, необходимые для формализации задачи конвертации.
Определение 1 (Реактивная UI‑система). Реактивная UI‑система — кортеж Ω = (S, A, T, view, update), где:
– S — конечное множество состояний приложения;
– A — конечное множество пользовательских действий (тапы, жесты, ввод текста и т.д.);
– T — множество деревьев представлений (view trees) над множеством компонентов C;
– view: S → T — тотальная функция, отображающая состояние в дерево представлений;
– update: S × A → S — тотальная функция переходов состояний.
Данное определение формализует центральный принцип декларативных фреймворков: интерфейс есть чистая функция состояния, а пользовательские действия индуцируют детерминированные переходы между состояниями. Определение применимо как к SwiftUI, так и к React, что обосновывает корректность постановки задачи конвертации между ними.
Определение 2 (Поведенческая трасса). Для реактивной системы Ω = (S, A, T, view, update) с начальным состоянием s₀ ∈ S и последовательности действий σ = (a₁, a₂, …, aₙ) ∈ A* определим поведенческую трассу как последовательность наблюдаемых деревьев:
  trace(Ω, s₀, σ) = (view(s₀), view(s₁), …, view(sₙ)),
  где sᵢ = update(sᵢ₋₁, aᵢ) для i = 1, …, n.
Определение 3 (Поведенческая эквивалентность). Две реактивные системы Ω₁ = (S₁, A, T₁, view₁, update₁) и Ω₂ = (S₂, A, T₂, view₂, update₂) поведенчески эквивалентны (Ω₁ ≈ Ω₂), если существует отношение R ⊆ S₁ × S₂ такое, что:
  (1) (s₀¹, s₀²) ∈ R — начальные состояния связаны;
  (2) для всех (s₁, s₂) ∈ R и a ∈ A выполняется:
    (a) view₁(s₁) ≅ view₂(s₂) — структурная эквивалентность деревьев представлений;
    (b) (update₁(s₁, a), update₂(s₂, a)) ∈ R — переходы сохраняют отношение.
Это классическое определение бисимуляции, адаптированное для реактивных UI‑систем. Оно формализует интуитивное понятие «одинакового поведения»: при одинаковых действиях пользователя обе системы демонстрируют структурно эквивалентные интерфейсы.
3.2. Формализация задачи и модель конвейера конвертации
3.2.1. Формальная постановка задачи конвертации
Определение 4 (Задача конвертации). Пусть Σ_S — множество синтаксически корректных SwiftUI‑программ, Σ_T — множество синтаксически корректных React+TypeScript проектов. Каждая программа src ∈ Σ_S индуцирует реактивную систему Ω_S(src), и каждый проект tgt ∈ Σ_T индуцирует реактивную систему Ω_T(tgt). Задача конвертации состоит в нахождении отображения conv: Σ_S → Σ_T такого, что для всех src ∈ Σ_S выполняется:
  Ω_S(src) ≈ Ω_T(conv(src)).
Полная поведенческая эквивалентность между SwiftUI‑ и React‑runtime в общем случае недостижима из‑за различий layout‑семантики, моделей реконсиляции и анимационных механизмов. Поэтому в рамках данной работы вводится ослабленное понятие корректности, проверяемое на трёх уровнях (структурная, поведенческая, визуальная корректность), и фиксируется ограниченное подмножество SwiftUI‑конструкций.
3.2.2. Модель конвейера как композиции отображений
Определение 5 (Промежуточные пространства). Определим следующие множества:
– IR — множество промежуточных представлений UI (UI‑IR), описывающих дерево компонентов, модель состояния, навигационную модель и модель анимаций;
– WebIR — множество веб‑промежуточных представлений, содержащих React‑скелет (skeleton) и список неразрешённых фрагментов (unresolved);
– Ctx — множество RAG‑контекстов (подмножество корпуса примеров);
– Log — множество логов валидации (сообщения об ошибках компиляции и тестов).
Определение 6 (Этапы конвейера). Конвейер конвертации определяется как композиция следующих отображений:
  (1) Экстрактор E: Σ_S → IR — извлечение UI‑IR из SwiftUI‑кода путём регулярного разбора (без полного AST Swift), включая построение дерева компонентов, извлечение переменных состояния, привязок и параметров навигации;
  (2) Маппер M: IR → WebIR — детерминированное правило‑ориентированное отображение базовых конструкций (VStack → flex‑column, Text → span, Button → button и т.д.) с формированием списка неразрешённых фрагментов;
  (3) Ретривер R: IR → Ctx — извлечение top‑k наиболее релевантных примеров из RAG‑корпуса на основе совпадения тегов (типы узлов, модификаторы, наличие состояния/привязок);
  (4) Генератор G: WebIR × Ctx × Σ_S → Σ_T — генерация целевого проекта с помощью LLM на основе скелета, RAG‑контекста и исходного SwiftUI‑кода;
  (5) Валидатор V: Σ_T → {0, 1} × Log — проверка корректности (TypeScript‑сборка и поведенческие тесты), возвращающая бинарный результат и лог ошибок;
  (6) Функция ремонта F: Σ_T × Log → Σ_T — генерация исправлений с помощью LLM на основе лога ошибок.
3.2.3. Конфигурации как подкомпозиции конвейера
Определение 7 (Конфигурации эксперимента). Для исследования вклада отдельных компонентов определяются пять конфигураций, образующих цепочку по включению:
  B0raw(src) = G(∅, ∅, src) — чистая LLM‑генерация только по исходному SwiftUI‑коду;
  B0(src) = G(E(src), ∅, src) — LLM‑генерация с UI‑IR как дополнительным контекстом;
  B1(src) = G(M(E(src)), ∅, src) — rule‑mapping + LLM;
  B2(src) = G(M(E(src)), R(E(src)), src) — rule‑mapping + RAG + LLM;
  B3(src) = RepairLoop(B2(src), V, F, K_max) — полный метод с контуром автопочинки.
Определение 8 (Частичный порядок конфигураций). На множестве конфигураций определяется частичный порядок по информационному включению:
  B0raw ⊑ B0 ⊑ B1 ⊑ B2 ⊑ B3,
  где C₁ ⊑ C₂ означает, что C₂ использует все этапы конвейера, задействованные в C₁, и, возможно, дополнительные.
3.2.4. Формализация метрик качества
Определение 9 (Метрики качества). Для целевого проекта t ∈ Σ_T определяются:
  build(t) ∈ {0, 1} — успешность TypeScript‑сборки;
  test(t) ∈ {0, 1} — успешность поведенческих тестов (при условии build(t) = 1; если build(t) = 0, то test(t) = 0).
Определение 10 (Агрегированные метрики). Для датасета D = {src₁, …, srcₙ} и конфигурации C определяются:
  BuildRate(C, D) = (1/n) · Σᵢ₍₁ⁿ build(C(srcᵢ));
  TestRate(C, D) = (1/n) · Σᵢ₍₁ⁿ test(C(srcᵢ)).
Определение 11 (Качество на решётке). Определим решётку качества для отдельного образца как тройку L = ({⊥, β, τ}, ≤), где:
  ⊥ — сборка не прошла (build = 0);
  β — сборка прошла, тесты не прошли (build = 1, test = 0);
  τ — сборка и тесты прошли (build = 1, test = 1);
  ⊥ ≤ β ≤ τ.
Это полная конечная решётка с наименьшим элементом ⊥ и наибольшим элементом τ. Для датасета из n образцов вектор качества принадлежит произведению решёток Lⁿ.
3.3. Формальная верификация алгоритма
3.3.1. Определение контура автопочинки
Определение 12 (Контур автопочинки). Для исходного кода src ∈ Σ_S и лимита итераций K_max ∈ ℕ контур автопочинки определяется как последовательность {tₖ}ₖ₍₀ᴷ:
  t₀ = B2(src);
  tₖ₊₁ = F(tₖ, log(tₖ)),   если V(tₖ) = (0, log(tₖ)) и k < K_max;
  tₖ₊₁ = tₖ,                 если V(tₖ) = (1, ∅) (неподвижная точка).
Итоговый результат: B3(src) = t_K, где K = min{k : V(tₖ) = (1, ∅)} ∨ K = K_max.
3.3.2. Теорема о завершимости
Теорема 1 (Завершимость контура автопочинки). Для любого src ∈ Σ_S и K_max ∈ ℕ контур автопочинки завершается не более чем за K_max + 1 шагов.
Доказательство. Рассмотрим два случая.
  Случай 1: существует k* ≤ K_max такое, что V(t_{k*}) = (1, ∅). Тогда для всех k ≥ k* имеем tₖ = t_{k*} (неподвижная точка), и цикл завершается на шаге k*.
  Случай 2: для всех k ≤ K_max выполняется V(tₖ) = (0, logₖ). Тогда цикл выполняет ровно K_max итераций ремонта и завершается.
В обоих случаях выполняется не более K_max + 1 вычислений (одна начальная генерация и до K_max итераций ремонта). Каждая итерация включает один вызов LLM (ограниченный по времени ответа модели) и одну валидацию (ограниченную временем сборки и тестирования). Следовательно, общее время ограничено (K_max + 1) · (T_llm + T_val), где T_llm и T_val — верхние границы времени вызова LLM и валидации соответственно. □
3.3.3. Теорема о неухудшении качества при ремонте
Для доказательства свойства неухудшения вводится следующее допущение о функции ремонта.
Допущение 1 (Сохранение прошедших проверок). Функция ремонта F удовлетворяет свойству: если V(t) = (1, ∅), то F(t, ∅) = t, т.е. проекты, прошедшие валидацию, не модифицируются.
Теорема 2 (Неухудшение качества при ремонте). При выполнении Допущения 1, для решётки качества L = ({⊥, β, τ}, ≤) и последовательности {tₖ}, порождённой контуром автопочинки, выполняется:
  q(t_K) ≥ q(t₀),
  где q: Σ_T → L — функция качества отдельного образца.
Доказательство. Рассмотрим случаи по значению q(t₀).
  Случай q(t₀) = τ: по Допущению 1 tₖ = t₀ для всех k, следовательно q(t_K) = τ = q(t₀).
  Случай q(t₀) = β: ремонт применяется к t₀. Результат q(t₁) ∈ {⊥, β, τ}. Если q(t₁) = τ, то цикл завершается. Если q(t₁) ∈ {⊥, β}, ремонт продолжается. На уровне агрегированных метрик для всего датасета неухудшение обеспечивается тем, что ремонт применяется только к несвалидированным образцам, а валидные образцы сохраняются.
  Случай q(t₀) = ⊥: аналогично, q(t_K) ∈ {⊥, β, τ}.
Для случаев β и ⊥ неухудшение на уровне отдельного образца не гарантируется в общем случае (LLM может ухудшить результат). Однако на уровне агрегированных метрик по датасету D выполняется:
  BuildRate(B3, D) ≥ BuildRate(B2, D),
поскольку если build(B2(srcᵢ)) = 1, то по Допущению 1 build(B3(srcᵢ)) = 1. Для образцов с build(B2(srcᵢ)) = 0 ремонт может привести к build = 1, что увеличивает агрегированную метрику. Понижение агрегированной BuildRate невозможно. □
3.3.4. Теорема о сходимости последовательности конфигураций
Теорема 3 (Ограниченность и сходимость). Последовательность агрегированных метрик качества по конфигурациям {BuildRate(Cₖ, D)}ₖ₍₀⁴, где C₀ = B0raw, C₁ = B0, C₂ = B1, C₃ = B2, C₄ = B3, обладает следующими свойствами:
  (1) Ограниченность: 0 ≤ BuildRate(Cₖ, D) ≤ 1 для всех k;
  (2) Строгая монотонность перехода B2→B3 (по Теореме 2): BuildRate(B3, D) ≥ BuildRate(B2, D);
  (3) Сходимость: последовательность сходится к sup{BuildRate(Cₖ, D)} = BuildRate(B3, D) ≤ 1.
Для переходов B0raw→B0→B1→B2 монотонность является эмпирической гипотезой, верифицируемой экспериментально. Формально она выполняется при следующем допущении.
Допущение 2 (Неухудшение качества при обогащении контекста). Дополнительный контекст (UI‑IR, React‑скелет, RAG‑примеры), включённый в промпт LLM, не ухудшает качество генерации в среднем по датасету:
  E[q(G(context₂, src))] ≥ E[q(G(context₁, src))], если context₁ ⊆ context₂.
Это допущение согласуется с результатами исследований по влиянию контекста на качество генерации кода LLM [3][5] и верифицируется экспериментально в разделе 3.5.
Следствие 1. При выполнении Допущений 1 и 2 и для конечного датасета D последовательность качества образует монотонно неубывающую ограниченную последовательность в [0, 1], которая сходится к значению BuildRate(B3, D).
Аналогичные утверждения справедливы для TestRate с заменой build на test.

5. Стоимостной анализ показал, что полный метод увеличивает расход токенов в 1,84 раза по сравнению с бейзлайном, при этом наиболее эффективным компонентом по соотношению «качество/стоимость» является RAG‑модуль.

В рамках данной выпускной квалификационной работы разработан и исследован гибридный алгоритм конвертации SwiftUI‑кода в веб‑представление на базе React + TypeScript с применением больших языковых моделей. Основные результаты работы состоят в следующем.

1. Проведён анализ предметной области и существующих подходов к автоматической трансляции UI‑кода. Показано, что rule‑only и LLM‑only подходы по отдельности недостаточны: первый ограничен покрытием, второй — воспроизводимостью и проверяемостью. Обоснован выбор гибридной стратегии, объединяющей детерминированное сопоставление конструкций, генерацию с помощью LLM, RAG‑подбор примеров и итеративную автоматическую валидацию.
2. Спроектирована и реализована архитектура конвертера, включающая шесть модулей: SwiftUI Extractor (извлечение UI‑IR), Rule Mapper (детерминированное отображение базовых конструкций), RAG Retriever (подбор релевантных примеров), LLM Generator (генерация React+TypeScript кода), Validator (TypeScript‑сборка и поведенческие тесты) и Repair Loop Controller (итеративная автопочинка). Введено промежуточное представление UI‑IR, выступающее семантическим контрактом между этапами конвейера.
3. Разработана теоретико‑множественная формальная модель декларативного пользовательского интерфейса, описывающая представления, состояние, модификаторы, привязки и реактивный цикл обновления. Модель формализована для SwiftUI и обобщена до универсальной абстракции, применимой к широкому классу UI‑систем (React, Jetpack Compose, UIKit). Данная модель подготовлена к публикации в рамках статьи «A Verified Core Model for Reactive User Interfaces: From SwiftUI to Cross‑Framework Semantics» [12].
4. Предложена формальная модель конвейера конвертации как композиции отображений на промежуточных пространствах. Доказаны теоремы о завершимости контура автопочинки и неухудшении агрегированного качества при ремонте. Эмпирически верифицировано допущение о монотонности обогащения контекста, обеспечивающее сходимость качества по конфигурациям.
5. Проведена экспериментальная валидация на стратифицированном датасете из 108 SwiftUI‑примеров, покрывающих layout‑контейнеры, базовые элементы, состояние и привязки, списки, навигацию и простые анимации. Полный метод (конфигурация B3) достигает 100% успешной TypeScript‑сборки и 83,3% прохождения поведенческих тестов, превосходя бейзлайн LLM‑only (B0raw: 88,9% сборки, 75,9% тестов).

Научная новизна работы заключается в:
– разработке гибридного алгоритма конвертации SwiftUI→React, объединяющего rule‑mapping, RAG и LLM с многоуровневой валидацией и автопочинкой, что является первым описанным в литературе подходом данного класса для задачи конвертации декларативного UI;
– создании теоретико‑множественной формальной модели декларативного UI, обобщаемой на произвольные фреймворки и пригодной для формального анализа, верификации и трансформаций;
– формальной модели конвейера конвертации с доказательством свойств завершимости и неухудшения качества.
Практическая значимость определяется возможностью использования разработанного решения как основы для:
– инструментов кроссплатформенного предпросмотра SwiftUI‑интерфейсов в браузере;
– интеграции UI‑проверок в CI/CD‑конвейеры без зависимости от macOS;
– образовательных платформ, позволяющих студентам изучать SwiftUI без доступа к оборудованию Apple.
Направления дальнейшего развития включают:
– расширение поддерживаемого подмножества SwiftUI (сложные анимации, UIViewRepresentable‑мосты, Environment);
– улучшение конвертации навигации и привязок через специализированные rule‑mapping правила и расширение RAG‑корпуса;
– интеграцию визуальной регрессии (screenshot comparison) как дополнительного уровня валидации;
– исследование переносимости алгоритма на другие пары фреймворков (Jetpack Compose → React, Flutter → React);
– разработку верифицированного пайплайна трансформации на основе формальной модели с доказательством сохранения семантики.
